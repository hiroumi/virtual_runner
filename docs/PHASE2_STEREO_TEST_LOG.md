対象: Virtual Boy for Nintendo Switch アクセサリ向け立体視レーシングゲーム・プロトタイプ

前提: [[docs/PHASE1_CALIBRATION_LOG.md]] のとおり、実機キャリブレーション済みの `config.json`（left/right viewport, swap_eyes, flip設定, fullscreen等）が確定済み。本作業ではこれらの値には一切手を加えていない。

## 2026-09-02: ビジュアル参考画像の受領

ユーザーより、赤黒基調の疑似3Dレーシングゲームの左右分割スクリーンショット（HUD、山、雲、ヤシの木、道路、プレイヤー車を含む構成）を参考画像として受領。

- 参考画像はあくまで**構図・配色（赤黒デュオトーン）・HUDレイアウトの参考**として扱い、車両デザイン（実在の市販車を思わせる形状）やロゴ等の著作物的要素は一切模倣していない。

## 実装内容

### `stereo_renderer.py`（Phase 1では未実装のプレースホルダーだったものを実装）

`calculate_disparity(depth, parallax_scale, cfg)` を全オブジェクト共通の視差計算APIとして実装：

```
raw = disparity_k * (1/depth - 1/screen_depth)
disparity = clamp(raw * parallax_scale, -max_negative_disparity_px, +max_disparity_px)

left_eye_x  = projected_x + disparity / 2
right_eye_x = projected_x - disparity / 2
```

- `screen_depth`（視差ゼロとなる基準奥行き）より手前のオブジェクトは自動的に正の視差（内向き＝交差視差＝手前に見える）、奥のオブジェクトは自動的に小さな負の視差（外向き）になる。カテゴリごとの特別処理は一切なく、depth値だけで両方の挙動が自然に得られる設計とした。
- ユーザー指定の符号規則（手前：左目→右方向／右目→左方向、奥：左目→左方向／右目→右方向）を式通りに実装し、実際に描画したピクセル位置でも意図通りの向きになっていることを確認済み（下記「動作確認」参照）。
- `max_disparity_px`（正の視差の上限）と `max_negative_disparity_px`（負の視差の上限）は `parallax_scale` を掛けた**後**にクランプされるため、`parallax_scale` をどれだけ上げても上限を超えない。これが「安全な上限」の実装。
- `StereoRenderer.draw_world(depth, draw_fn)` は draw_fn を左右それぞれ1回ずつ、符号付きオフセット込みで呼び出す。`draw_flat(draw_fn)` はHUD用の視差ゼロ版。ゲームロジックは常に1回だけ実行し、描画のみをこの層経由で左右に分岐させる設計とした（左右でシミュレーションを二重実行しない、というユーザー指示に準拠）。
- 垂直方向の視差は本システムには一切存在しない（x方向のオフセットのみ）。

### `config.json` への追加項目

既存のキャリブレーション値（viewport, swap_eyes, flip, fullscreen等）は変更せず、以下の4項目のみ追加：

```json
"screen_depth": 20.0,
"disparity_k": 250.0,
"max_disparity_px": 40.0,
"max_negative_disparity_px": 8.0
```

- `screen_depth`: 視差ゼロとなる基準奥行き（ワールド単位、任意の相対値）
- `disparity_k`: 奥行きから視差量への変換係数
- `max_disparity_px`: 正方向（手前）の視差の安全上限（px）
- `max_negative_disparity_px`: 負方向（奥）の視差の安全上限（px）

いずれも `config.json` から調整可能（既存の `parallax_scale` と同様）。

### `phase2_test_scene.py`（静的ステレオ確認シーン）

ユーザー指定の5要素を含む、動かない（スクロールしない）確認シーンを実装：

| 要素 | depth | 視差（parallax_scale=1.0時） |
|---|---|---|
| HUD（TIME/SCORE/SPEED） | — （視差ゼロ固定） | 0px |
| 空・雲、山 | 300 / 250 | -8.0px（クランプ、小さな外向き） |
| 遠くの車 | 22 | -1.1px（ほぼゼロ） |
| 中距離のヤシの木 | 11〜13 | +6.7〜+10.2px |
| 道路のダッシュマーカー（6個） | 4〜40 | 手前+40.0px 〜 奥-6.2px |
| 近くのヤシの木 | 6 | +29.2px |
| プレイヤー車 | 3 | +40.0px（クランプ、最大） |

- 道路については、単一の視差ではなく、6個のダッシュマーカーそれぞれに個別のdepthを与え、手前ほど強い内向き視差・奥ほどゼロに近い視差になることを実装（ユーザー指示の「道路セグメントごとに視差を計算」に対応）。
- デバッグオーバーレイに全オブジェクトのdepthと計算後disparityを常時表示。安全上限に達している場合は `(CLAMPED +/-)` と表示。
- 実行中の操作: `Up`/`Down`でparallax_scaleを増減、`Z`で視差を一時的に全ゼロ化、`I`で視差方向を反転（デバッグ用）、`S`で保存、`F`でフルスクリーン切替。

### 動作確認（この環境内、実機なし）

実機（Windows 11 + 実際のアクセサリ）がこのセッションから使えないため、以下はWSL上でSDLダミードライバを使った自動テストと、実際に1フレームをレンダリングした画像の確認にとどまる。**実際にレンズ越しにどう見えるかはユーザーによる実機確認が必要。**

- `pytest`: 20件全て成功（視差計算の単体テスト8件を含む — screen_depthでゼロになること、depthが増えるほど単調減少すること、正負とも安全上限を超えないこと、parallax_scale=0で全オブジェクトが視差ゼロになること等）。
- ヘッドレスで1フレームをレンダリングし、各オブジェクトのdisparity値と、実際に描画されたピクセル位置を確認。プレイヤー車は左目側で中心より右へ、右目側で中心より左へ描画されており（内向き＝交差視差）、山は左目側で中心より左へ、右目側で中心より右へ描画されている（外向き）ことを目視・座標計算の両方で確認し、ユーザー指定の符号規則と一致することを確認した。
- HUDが両目とも同一ローカル座標（視差ゼロ）で描画されることを確認。

## 申し送り事項（Claude Codeより）

- Phase 1完了時点の実機viewportサイズは280×282とほぼ正方形（1:1に近い）であり、当初Phase 2の想定候補として挙がっていたVirtual Boy的な384×224（横長、約1.71:1）という論理解像度とはアスペクト比が大きく異なる。このため、本テストシーンは384×224のような固定論理解像度を経由せず、各eyeのviewportサイズ（280×282）へ直接描画する方式とした。ゲーム本編でも、この実機のほぼ正方形のアスペクト比を前提に画面構成を設計するのが妥当と考えられる。
- `parallax_scale` / `screen_depth` / `disparity_k` / `max_*_disparity_px` の初期値は、見た目のバランスを見て仮に決めた値であり、実機で確認・調整することを前提としている。特に `max_disparity_px`（40px）は、この構成では実質「近景オブジェクトは常にこの値でクランプされる」設計になっている点に留意（安全上限として意図的な挙動）。
